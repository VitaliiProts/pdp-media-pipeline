# ADR-003. База даних: PostgreSQL

- Статус: Прийнято
- Дата: 2026-10-08

## Контекст

Сервіс Metadata зберігає `users`, `jobs`, `job_executions`, `audit_log`, а з Етапу 3 також
`outbox`, `inbox` і `idempotency_keys`. Ключові вимоги до сховища:

1. **Атомарність між станом і подією**: запис job і події в outbox в одній транзакції
   (transactional outbox), інакше задача губиться між БД і чергою.
2. **Машина станів з конкурентним доступом**: перехід `queued -> scheduled -> running -> ...`
   має бути умовним (`UPDATE ... WHERE id = $1 AND status = $from`), щоб два воркери не
   перевели задачу одночасно.
3. **Унікальність** для ідемпотентності: `UNIQUE (user_id, key)` в `idempotency_keys`, `UNIQUE
(message_id)` в inbox.
4. **Черга в таблиці** для outbox relay: кілька реплік relay без подвійної публікації, тобто
   `SELECT ... FOR UPDATE SKIP LOCKED`.
5. Запити `GET /jobs?status=` і пошук за `user_id` з пагінацією, тобто складені індекси.
6. Гнучкі `input` і `output` задач, різні для кожного типу.

## Рішення

Використовуємо **PostgreSQL 17**:

- `input`, `output` і payload подій зберігаються в `JSONB`;
- переходи станів через одну функцію з умовним `UPDATE` і перевіркою `rowCount`;
- outbox relay на `FOR UPDATE SKIP LOCKED`;
- ORM і міграції обираємо на Етапі 1 (Drizzle або Prisma).

## Альтернативи

### MongoDB

- Плюси: гнучка схема для `input`/`output`; `findOneAndUpdate` з умовою по статусу дає атомарний
  перехід в межах одного документа; change streams можуть замінити outbox relay.
- Мінуси: транзакції між колекціями (job + outbox) вимагають replica set навіть локально і
  дорожчі; немає прямого аналога `SKIP LOCKED`, конкурентний claim робиться через
  `findOneAndUpdate` з полем-лізом; change streams теж вимагають replica set і додають ще один
  механізм з власною семантикою resume token. Звітні запити (частка DLQ, latency за типами)
  простіші в SQL.

### Postgres + Redis для статусів

Гарячі статуси в Redis, історія в Postgres. Відхилено: дві системи істини для одного стану і
проблема узгодженості, яку ми якраз хочемо прибрати outbox'ом.

## Наслідки

- Позитивні: outbox, inbox, ідемпотентність і машина станів реалізуються стандартними засобами
  Postgres в одній транзакції; на захисті легко пояснити, «як гарантується, що задача не
  губиться між БД і чергою».
- Негативні: потрібні міграції і дисципліна схеми; `JSONB` без валідації в БД, тож схеми
  `input`/`output` перевіряємо zod у `libs/contracts`.
- Ризики: Postgres стає єдиною точкою відмови для запису. Треба обмежити розмір пулу з'єднань на
  репліку (з урахуванням HPA) і перевірити поведінку при недоступності БД chaos-тестом (Етап 6).
  Таблиці `outbox`, `inbox` і `audit_log` ростуть, потрібна політика очищення.
