# ADR-009. Вихідні запити і вебхуки

- Статус: Прийнято
- Дата: 2026-10-12

## Контекст

На Етапі 3b система вперше робить запити на адреси, які задає користувач:

1. **Джерело за URL.** `sourceUrl` у `image.resize` і `video.frames`: воркер сам завантажує файл.
2. **Вебхуки.** Після `succeeded` чи `dead` медіа-задачі система шле POST на зареєстровану адресу.

Обидва випадки — класичний SSRF: URL на `169.254.169.254` (метадані хмари), `localhost:5432`
чи внутрішній сервіс у кластері дає користувачу доступ туди, куди він не мав би діставатися.
Перевірка рядка URL не допомагає: DNS-імʼя може вказувати на приватну адресу, змінити її між
перевіркою й запитом (DNS rebinding) або відповісти редиректом.

Для вебхуків є ще дві проблеми. Приймач має відрізняти наш запит від підробленого. А приймач,
що лежить, відповідає повільно чи рве зʼєднання, не повинен ні губити подію, ні блокувати
воркер.

## Рішення

### `libs/egress`: один шлях для всіх вихідних запитів

`EgressClient.request(url, options)` використовують і Gateway (перевірка URL при створенні),
і воркери (завантаження, доставка).

- **Схема:** лише `http` і `https`, без логіна й пароля в URL.
- **Адреса:** DNS резолвиться з `all: true`. Якщо **будь-яка** адреса непублічна
  (loopback, RFC 1918, link-local, CGNAT, ULA, multicast, IPv4-mapped IPv6 тощо), запит
  відхиляється з `BLOCKED_ADDRESS`. Для IPv4 і IPv6 окремі `BlockList`, щоб правило
  `::ffff:0:0/96` не зачіпало звичайні IPv4.
- **Pinning:** зʼєднання відкривається на щойно перевірену адресу через власний `lookup`, з
  `agent: false`. Між перевіркою і запитом немає другого резолву, тож rebinding не працює.
- **Редиректи:** до 3, лише для GET. Кожен новий URL проходить ту саму перевірку. POST з `3xx`
  не переслідується.
- **Ліміти:** дедлайн на весь запит через `AbortSignal.timeout`, ліміт байтів за
  `Content-Length` і лічильником потоку. Паралельність на хост — `EGRESS_PER_HOST_CONCURRENCY`
  (4), щоб один повільний хост не забрав усі слоти.
- **Виняток:** хости з `EGRESS_PRIVATE_HOSTS` можуть мати приватні адреси. У compose це лише
  `webhook-receiver`; у продакшні список порожній.

Gateway перевіряє URL при створенні задачі й реєстрації вебхука і одразу відповідає `400`.
Воркер перевіряє ще раз перед кожним запитом, бо DNS міг змінитися.

| Код помилки                                                         | Клас      |
| ------------------------------------------------------------------- | --------- |
| `INVALID_URL`, `BLOCKED_ADDRESS`, `TOO_LARGE`, `TOO_MANY_REDIRECTS` | permanent |
| `RESOLVE_FAILED`, `TIMEOUT`, `NETWORK`                              | transient |

### Реєстрація вебхука

Таблиця `webhook_endpoints (id, user_id, url, secret, events[], created_at)` у Metadata.
Не більше 5 endpoint-ів на користувача; ліміт тримається блокуванням рядка користувача
(`FOR UPDATE`), щоб паралельні запити його не обійшли. Секрет `whsec_<base64 24 байти>`
повертається лише у відповіді на створення. Список його не показує, а читає його тільки воркер
доставки через internal API. Події: `job.succeeded`, `job.dead`.

### Доставка як задача

Доставка — звичайна задача `webhook.deliver` класу `io`. Ретраї, backoff з full jitter,
`JOB_MAX_ATTEMPTS`, `dead_reason`, DLQ і redrive з ADR-007 працюють для неї без окремого коду.

- Задачі доставки створюються **в тій самій транзакції**, що й перехід медіа-задачі в
  `succeeded` чи `dead`: по одній на кожен підписаний endpoint. Подія не губиться, навіть
  якщо Metadata впаде одразу після переходу.
- Сама доставка вебхуків не породжує: fan-out лише для медіа-типів.
- `input = { endpointId, messageId, payload }`. `messageId` (`msg_…`) генерується один раз і
  однаковий для всіх спроб і redrive, тож приймач може дедуплікувати.
- Endpoint видалили, поки доставка в черзі → `dead / permanent`.
- Доставки endpoint-а видно в `GET /v1/webhooks/:id/deliveries` і на сторінці «Вебхуки» у Web UI;
  «мертву» можна надіслати знову тим самим `POST /v1/jobs/:id/redrive`.

### Підпис: Standard Webhooks

Заголовки за [специфікацією Standard Webhooks](https://www.standardwebhooks.com/):

- `webhook-id: msg_…`;
- `webhook-timestamp: <unix seconds>`;
- `webhook-signature: v1,<base64(HMAC-SHA256(base64decode(secret без whsec_), "id.timestamp.body"))>`.

Підпис рахується в момент відправки, тож `webhook-timestamp` свіжий на кожній спробі, а приймач
може відкидати запити старші за 5 хв (захист від replay). `verifyWebhook` у `@pdp/contracts`
приймає кілька підписів через пробіл (ротація секрету) і порівнює через `timingSafeEqual`.

### Відповідь приймача

| Відповідь                                   | Клас      |
| ------------------------------------------- | --------- |
| `2xx`                                       | успіх     |
| `408`, `409`, `425`, `429`, `5xx`           | transient |
| Решта `4xx`, `3xx`                          | permanent |
| Таймаут (`WEBHOOK_TIMEOUT_MS`, 10 с), обрив | transient |

Тіло відповіді читається не більше 64 КБ і відкидається: важливий лише статус.

## Наслідки

- **Плюс:** критерій етапу виконується без спеціального коду: «поганий» приймач отримує подію
  після ретраїв, або вона закінчується в `JOBS_DLQ` як `exhausted` чи `permanent`.
  Інтеграційний тест перевіряє обидва шляхи на тестовому приймачі з compose.
- **Плюс:** усі вихідні запити йдуть через один модуль з тестами на приватні адреси,
  rebinding і редиректи. Новий код не може випадково піти в мережу в обхід перевірок.
- **Плюс:** стандартний формат підпису: приймач може перевіряти його готовими бібліотеками.
- **Мінус:** доставка ділить ліміт спроб і backoff з медіа-задачами. При `JOB_MAX_ATTEMPTS = 5` і
  cap 60 с приймач, що лежить кілька хвилин, отримає подію лише після ручного redrive.
  Для вебхуків зазвичай ретраять годинами; окремий бюджет спроб можна додати пізніше.
- **Мінус:** порядок подій не гарантується: `job.dead` після redrive і `job.succeeded` можуть
  прийти в будь-якому порядку. Приймач орієнтується на `timestamp` і `jobId`.
- **Ризик:** pinning обходить системний DNS-кеш і проксі. Якщо в продакшні буде egress-проксі,
  перевірку адрес треба перенести туди.

## Альтернативи

- **Перевіряти лише рядок URL або резолвити окремо від запиту.** Не захищає від DNS rebinding:
  між перевіркою і `connect` адреса може змінитися.
- **Egress-проксі (Smokescreen) замість бібліотеки.** Правильніше на рівні кластера, але
  потребує ще одного сервісу і не дає типізованих помилок для класифікації. Бібліотека не
  заважає додати проксі пізніше.
- **Окремий сервіс доставки вебхуків або Svix.** Svix дає довгі ретраї й портал для приймачів,
  але це зовнішня залежність. Окремий сервіс дублював би ретраї, DLQ і redrive, які вже є для
  задач.
- **Публікувати вебхуки з outbox-relay напряму.** Relay мав би робити HTTP-запити до чужих
  серверів, тобто повільний приймач гальмував би публікацію всіх подій.
- **Підпис при створенні доставки.** Тоді `webhook-timestamp` застарівав би на ретраях і
  приймач з перевіркою вікна відкидав би коректні повторні спроби.
