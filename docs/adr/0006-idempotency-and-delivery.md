# ADR-006. Ідемпотентність і семантика доставки

- Статус: Прийнято
- Дата: 2026-10-12
- Перевірка під збоями: [звіт Етапу 6](../../perf/reports/stage-6.md)

## Контекст

JetStream дає **at-least-once**: повідомлення, на яке не прийшов ack, буде доставлене знову.
Exactly-once на рівні брокера неможливий, бо між «зробив роботу» і «надіслав ack» завжди є
момент, коли процес може впасти. PDP вимагає, щоб задача не губилась і **не виконувалась двічі
з видимим ефектом**, а повторний `POST /jobs` з тим самим ключем не створював нової задачі.

Дублікати виникають у чотирьох місцях:

1. **Клієнт → Gateway.** Таймаут відповіді, клієнт повторює `POST /v1/jobs`.
2. **Metadata → NATS (outbox relay).** Падіння між publish і `published_at = now()`.
3. **Scheduler → NATS (dispatch).** Падіння між publish dispatch і переходом у `scheduled`.
4. **NATS → Worker.** Ack загубився після того, як воркер уже завершив задачу.

Що вже було з Етапу 1:

- outbox у транзакції зі зміною стану;
- `Nats-Msg-Id` для подій і dispatch, вікно дедупу 2 хв;
- ідемпотентні переходи за `(jobId, attempt, to)` у `job_transitions`;
- результати пишуться за детермінованими ключами `results/<jobId>/<preset>.webp`.

## Рішення

Семантика: **at-least-once доставка + ідемпотентні споживачі = effectively-once ефект.**
Кожен із чотирьох випадків закривається окремо.

### 1. `Idempotency-Key` на `POST /v1/jobs`

- Заголовок необов'язковий, 1–255 друкованих ASCII-символів, область дії — користувач.
- Gateway рахує `requestHash = sha256` канонічного JSON (ключі відсортовані) з
  `{type, priority, input}`; пріоритет береться вже з дефолтом.
- Metadata в транзакції створення:
  1. `pg_try_advisory_xact_lock(hashtextextended(user_id || ':' || key, 0))`. Не вдалося взяти
     lock → `409 IDEMPOTENCY_KEY_IN_PROGRESS`: такий самий запит зараз виконується.
  2. Видаляє прострочений запис для цього ключа (старший за `IDEMPOTENCY_TTL_HOURS = 24`).
  3. Є запис з іншим `requestHash` → `422 IDEMPOTENCY_KEY_REUSED`.
  4. Є запис з тим самим hash → повертає збережений `JobDto`, `replayed: true`.
  5. Немає запису → створює job, подію, audit і рядок `idempotency_keys` з відповіддю.
- Gateway відповідає `202` в обох випадках; повтор позначено заголовком `Idempotent-Replayed: true`.
- Lock знімається на commit, коли запис уже видно, тож конкурентний запит або бачить зайнятий
  ключ, або знаходить готову відповідь. Двох задач на один ключ не буває.
- Janitor раз на 10 хв видаляє прострочені ключі. Термін також перевіряється при використанні,
  тож janitor лише тримає таблицю малою, і запускати його на кількох репліках безпечно.
- Web UI генерує ключ один раз на завантаження (`crypto.randomUUID()`) і повторює його в усіх
  ретраях після `429`/`503`.

### 2–3. Публікації в NATS

Лишаються на `Nats-Msg-Id`. Для dispatch id тепер містить покоління:
`dispatch:<jobId>:<attemptBase>`, бо redrive мусить створити **новий** dispatch, а повтор
`job.created` того самого покоління — ні. Відкинуті JetStream дублікати рахуються в
`jobs_duplicates_total{source="outbox"|"dispatch"}` за полем `duplicate` у PubAck.

### 4. Inbox воркера

Таблиця `inbox (consumer, message_id, job_id, processed_at)` у Metadata:

- `consumer` — durable-ім'я (`worker-cpu`, `worker-priority`), `message_id = dispatch:<jobId>:<attemptBase>`;
- воркер передає `inbox` у переходах `running`, `succeeded` і `dead`;
- рядок пишеться **в тій самій транзакції**, що й фінальний перехід (`succeed` або `dead`);
- перехід, що приходить з уже обробленим `inbox` і ще не застосований, отримує
  `409 DUPLICATE_DELIVERY`; воркер робить ack без обробки, лічильник
  `jobs_duplicates_total{source="inbox"}` зростає.

Перевірка йде після пошуку в `job_transitions`: точний повтор того самого переходу (ретрай HTTP
воркером) лишається no-op, а не помилкою.

### Що це дає разом

| Збій                                  | Що відбувається                                                                  |
| ------------------------------------- | -------------------------------------------------------------------------------- |
| Клієнт повторив `POST` після таймауту | Та сама задача, `Idempotent-Replayed: true`                                      |
| Relay впав між publish і commit       | Republish з тим самим `eventId`, JetStream відкидає                              |
| Scheduler впав до `scheduled`         | Повтор `job.created`, dispatch з тим самим id відкидається                       |
| Воркер упав посеред обробки           | Redelivery, нова спроба, стара `abandoned`; результати перезаписуються ідентично |
| Ack загубився після `succeeded`       | Redelivery → `DUPLICATE_DELIVERY` → ack без обробки                              |

## Наслідки

- **Плюс:** кожен дублікат видно в метриці з джерелом; тест «вбити воркер посеред обробки» і
  тест «загублений ack» перевіряють це на справжньому NATS і Postgres.
- **Плюс:** inbox у Metadata, а не у воркері: воркер лишається stateless, а запис іде в одній
  транзакції зі зміною статусу, тобто без вікна між ними.
- **Мінус:** зайвий рядок на кожну завершену задачу. Таблиця росте як `jobs`; чистити її разом
  з архівацією задач (Етап 5).
- **Мінус:** `Idempotency-Key` прив'язаний до Metadata. Якщо Metadata недоступна, повтор
  отримає `503`, а не збережену відповідь. Це прийнятно: без Metadata задачу все одно не створити.
- **Обмеження:** replay перевіряє backpressure і наявність source раніше, ніж Metadata. Повтор
  при повній черзі отримає `503` з `Retry-After`, а не збережену відповідь, і клієнт повторить пізніше.

## Альтернативи

- **Redis для Idempotency-Key** (`SET NX` з TTL). Швидше, але задача й ключ у різних сховищах:
  падіння між ними дає або задачу без ключа (дубль при повторі), або ключ без задачі. У Postgres
  це одна транзакція.
- **Унікальний індекс `(user_id, key)` без advisory lock.** Другий конкурентний запит чекав би
  на row lock до commit першого і отримав би unique violation; треба було б розрізняти «ще
  виконується» і «вже є». Advisory lock дає явний `409` одразу, без очікування.
- **Inbox у Redis або локальна LRU у воркері.** Не переживає рестарт і не атомарна з переходом.
- **Лише `job_transitions` без окремого inbox.** Покриває більшість випадків через `JOB_TERMINAL`,
  але не дає явного сигналу «це дублікат доставки», а PDP вимагає дедуп як окремий механізм із
  метрикою.
