# ADR-002. Черга: NATS JetStream

- Статус: Прийнято
- Дата: 2026-10-08
- Підстава: [спайк 01](../spikes/01-jetstream-vs-bullmq.md)

## Контекст

Потрібен брокер між Gateway/Metadata, Scheduler і воркерами. Вимоги:

- не губити задачі при падінні воркера чи рестарті поду;
- окремі черги для класів `io`, `cpu`, `priority` з власними лімітами;
- ретраї з затримкою, DLQ і redrive;
- дедуплікація на боці продюсера (outbox relay може опублікувати подію двічі);
- довгі задачі (транскодинг хвилинами) без хибних повторних доставок;
- метрика глибини черги для backpressure і KEDA;
- Redis у системі вже використовується для rate limiting.

### Семантика доставки

- **At-most-once**: ack до обробки. Падіння посеред роботи губить задачу. Для нас неприйнятно.
- **At-least-once**: ack після обробки. Падіння до ack дає повтор. Це те, що дають і JetStream,
  і BullMQ.
- **Effectively-once**: at-least-once плюс ідемпотентний обробник (inbox-таблиця, детерміновані
  ключі результатів, `Nats-Msg-Id` для дедупу публікації). Справжнього exactly-once між брокером,
  БД і S3 немає: це завжди властивість системи, а не брокера.

Ціль системи: **effectively-once**. Брокер має давати надійний at-least-once і інструменти
для дедупу.

## Рішення

Використовуємо **NATS JetStream**:

- стріми з retention `WorkQueue` на клас: `JOBS_IO`, `JOBS_CPU`, `JOBS_PRIORITY`; окремий `JOBS_DLQ`;
- durable **pull** consumers з `AckPolicy.Explicit`, явними `AckWait`, `MaxDeliver`,
  `MaxAckPending` на кожен клас;
- `Nats-Msg-Id = eventId` при публікації з outbox, `duplicate_window` більший за максимальну
  затримку relay;
- ретраї через `nak(delay)` з backoff і full jitter, рахуємо в коді воркера;
- permanent-помилки: копія в `JOBS_DLQ`, потім `term()`;
- довгі задачі: `msg.working()` з періодом меншим за `AckWait`.

## Альтернативи

### BullMQ (Redis)

- Плюси: найшвидший старт; вбудовані backoff, стан `failed` як DLQ, пріоритети, delayed jobs,
  UI (Bull Board). У спайку ретраї й відновлення після `kill -9` працювали без власного коду.
- Мінуси: лише Node; Redis без кворумної реплікації (failover Sentinel може втратити останні
  записи); черги й rate limiter на одному Redis означають спільну точку відмови і спільний
  бюджет пам'яті. Дедуп за `jobId` мовчки ігнорує дубль без сигналу продюсеру. Продовження lock
  неявне: якщо event loop заблокований ffmpeg-обробкою в тому ж процесі, lock спливає.

### Kafka

- Плюси: стандарт для event streaming, висока пропускна здатність, довге зберігання.
- Мінуси: модель партицій не підходить для черги задач: паралелізм обмежений кількістю партицій,
  немає per-message ack і затримки повтору, ретраї через окремі retry-топіки. Операційно важче
  (KRaft, брокери), для 3 jobs/с це надмірно.

### RabbitMQ

- Плюси: зрілий брокер задач, per-message ack, DLX, quorum queues, priority queues.
- Мінуси: затримані повтори потребують плагіна або TTL+DLX; ще одна технологія поруч із NATS,
  який нам однаково зручний для подій між сервісами. Сильної переваги над JetStream для нашого
  кейсу немає.

## Наслідки

- Позитивні: один брокер і для черг задач, і для подій (`job.created`, `job.status_changed`);
  явна і перевірювана семантика (спайк показав рівно ті повтори, які очікувались); дедуп
  публікації з явним `duplicate=true`; KEDA має NATS JetStream scaler; Redis лишається лише для
  rate limiting.
- Негативні: DLQ, backoff і redrive пишемо самі. Після вичерпання `MaxDeliver` повідомлення
  лишається в WorkQueue-стрімі, тож воркер має сам перенести його в DLQ на останній спробі.
  Вищий поріг входу (streams, consumers, advisories).
- Ризики: спайк показав, що без heartbeat задача, довша за `AckWait`, виконується двома
  воркерами **паралельно**, і обидва ack приймаються. Отже inbox і ідемпотентний обробник
  обов'язкові з Етапу 3, а `AckWait` і період `working()` налаштовуються окремо для кожного класу.
