# ADR-013. Автентифікація користувачів

- Статус: Прийнято
- Дата: 2026-10-14

## Контекст

До цього етапу Gateway приймав лише `X-API-Key`. Це зручно для скриптів і k6, але браузерний UI
Етапу 5c потребує звичайного входу: email і пароль, сесія в cookie, керування кількома API-ключами
з налаштувань. Критерій 5c.1: реєстрація і вхід через публічний API, сесія або ключ на кожному
захищеному запиті, наявні ключі продовжують працювати після міграції.

Обмеження PDP: немає поштової розсилки, немає окремого IdP, Redis уже є в стеку (ADR-005),
Metadata — єдине джерело правди про користувачів, а Gateway — єдина точка, що говорить з
браузером.

## Рішення

### Власні паролі, не OAuth

Користувач реєструється email'ом і паролем. Пароль хешується **argon2id** у Metadata
(`@node-rs/argon2`, параметри OWASP Password Storage Cheat Sheet: memory 19 MiB, time 2,
parallelism 1). Email зберігається в нижньому регістрі з унікальним індексом на `lower(email)`.
Пароль — 8–128 символів, без правил складності: довжина важливіша за «має бути велика літера».

OAuth (Google тощо) відкладено: для PDP це зайва зовнішня залежність і кілька днів на callback,
а пароль у власному сховищі достатній, щоб показати правильну модель збереження секретів.

**Свідомо поза PDP:** відновлення пароля і підтвердження email. Обидва потребують поштової
розсилки і шаблонів листів; без них користувач у локальному стеку створюється з робочим
паролем одразу.

### Cookie-сесія в Redis, не JWT

Після реєстрації або входу Gateway створює випадковий токен (`randomBytes(32)`, base64url) і
кладе в Redis ключ `session:{sha256(token)}` зі значенням `{ userId, createdAt }`. Клієнту йде
cookie `pdp_session`: `HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` з конфігу
(`SESSION_COOKIE_SECURE`, за замовчуванням `true` — Chrome і Firefox приймають його на
`*.localhost` без HTTPS).

TTL — два шари: idle через `GETEX` (`SESSION_IDLE_TTL_S`, 7 днів) і абсолютний вік
(`SESSION_MAX_AGE_S`, 30 днів; він же `Max-Age` cookie). Кожен новий вхід видає новий токен і
знищує попередню сесію з cookie — захист від session fixation.

JWT відхилено: відкликання потребувало б чорного списку в Redis (ті самі залежності, гірший
контракт), а розмір токена і криптографія не дають користі для same-origin UI. Сесія в Redis
відкликається одним `DEL` на logout.

### Redis недоступний: сесії fail-closed, ключі працюють

Rate limiting лишається fail-open (ADR-005). Сесії — навпаки: помилка Redis → `503` з
`Retry-After: 5`, щоб клієнт не отримав «неавторизовано» замість тимчасової недоступності і не
скинув cookie. Запити з `X-API-Key` Redis не чіпають, тож скрипти й k6 працюють під час
аварії сесійного сховища.

### Guard: сесія або API-ключ

`AuthGuard` дивиться на заголовок `X-API-Key`: якщо він є — делегує `ApiKeyGuard` і ставить
`authMethod = 'api-key'`. Інакше читає cookie, для методів що змінюють дані перевіряє `Origin`,
розв'язує сесію і ставить `authMethod = 'session'`. `GET /v1/me` повертає користувача разом із
методом: UI і діагностика бачать, чим підписаний запит.

API-ключі переїхали з колонок `users` у таблицю `api_keys` (кілька на користувача, `last_used_at`,
`revoked_at`). Міграція копіює наявний ключ як `name = 'default'`, тож старі ключі лишаються
валідними. Створювати й відкликати ключі можна лише з сесії: витік одного ключа не дозволяє
намінтити нові. Ліміт — `API_KEY_MAX_PER_USER` (10). Відкликання доходить до всіх реплік Gateway
за час `API_KEY_CACHE_TTL_MS` (60 с).

### Origin і CSRF

Браузерні запити з cookie захищає перевірка `Origin` проти списку `APP_ORIGINS` (compose —
Web UI і Vite; k3d — `http://app.pdp.localhost:19080`; prod — `https://app.example.com`). Чужий
Origin завжди `403`. Відсутній Origin відмовляється лише на небезпечних методах із сесією і на
logout із cookie; login і register дозволяють відсутній Origin (curl, k6). `SameSite=Lax`
додатково блокує cookie на cross-site POST з чужих сайтів.

### Захист від перебору

`RateLimiterService.checkAuth(ip, email?)` — той самий GCRA у Redis, що й решта лімітів
(ADR-005). Ключі `rl:auth:ip:{ip}` і `rl:auth:email:{sha256(email)}`. За замовчуванням: IP
10/хв із burst 20; email 1/хв із burst 5. Реєстрація рахує лише IP. Невідомий email і
неправильний пароль дають одну й ту саму відповідь `401 invalid email or password`; для
відсутнього користувача Metadata все одно ганяє argon2 проти dummy-хеша, щоб час відповіді не
розрізняв випадки.

Метрики: `auth.logins{outcome=…}` і `auth.registrations{outcome=…}` (у VictoriaMetrics —
`auth_logins_total`, `auth_registrations_total`). Алерт `LoginFailuresSpike` — ticket, коли
невдалих і throttled входів більше 30 на хвилину протягом 5 хв.

### Міграція expand / contract

У локальному стеку одна ревізія (0006 додає `api_keys` і колонки, 0007 копіює ключі й дропає
старі колонки) застосовується одразу. У продакшені з кількома репліками Metadata дроп колонок,
які старий код ще читає, треба рознести: спершу expand (нова таблиця + бекфіл, подвійний запис),
потім contract (прибрати колонки після деплою нового коду). Для PDP compose і одного релізу
k3d це зайве; застереження лишається в цьому ADR.

Логи Gateway редагують `cookie` і `set-cookie`, щоб токен сесії не потрапив у VictoriaLogs.

## Наслідки

- Браузерний UI отримує стандартний вхід без змін у контрактах задач і вебхуків.
- Скрипти, k6 і seed-user лишаються на `X-API-Key`; Web UI до 5c.4 може користуватися ключем
  як раніше.
- Redis стає критичним для сесій (але не для API-ключів); персистентність і вибір ElastiCache —
  у Етапі 6 / ADR-017.
- Немає «забув пароль» і немає підтвердження email: для демо й локальної розробки це прийнятно,
  для відкритого продакшену — ні.
- Керування ключами лише з сесії зменшує радіус витоку ключа.

## Альтернативи

### JWT у cookie або Authorization

Плюс: Gateway не ходить у Redis на кожен запит. Мінус: відкликання потребує чорного списку або
короткого TTL із refresh; розмір токена й криптографія не потрібні same-origin UI. Відхилено.

### OAuth-only (Google)

Плюс: немає паролів у нашій БД. Мінус: зовнішня залежність, callback, локальний стек без
інтернету, і все одно потрібні API-ключі для скриптів. Відкладено.

### Сесії в PostgreSQL

Плюс: одне сховище. Мінус: кожен захищений запит б'є в Metadata/PG; idle TTL і fail-closed
простіші в Redis, який уже є для rate limit. Відхилено.

### CSRF-токен замість Origin

Плюс: працює й без заголовка Origin. Мінус: окремий cookie/заголовок на кожен мутуючий запит,
складніший фронтенд. Same-origin UI з фіксованим списком `APP_ORIGINS` покриває загрозу
простіше. Відхилено для PDP.
