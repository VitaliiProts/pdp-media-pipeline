# ADR-005. Алгоритм rate limiting: GCRA у Redis

- Статус: Прийнято
- Дата: 2026-10-12

## Контекст

PDP вимагає, щоб API тримав **20 rps на користувача і 200 rps глобально** і відповідав `429` з
коректним `Retry-After`. Gateway працює в кількох репліках (HPA з Етапу 5), тож стан лімітів
має бути спільним: це Redis, який уже є в compose.

Вимоги до алгоритму:

1. **Точний `Retry-After`.** Клієнт має знати, коли повторювати, а не вгадувати з backoff.
2. **Обидва ліміти за одну операцію.** Перевірка користувача і глобальна мають бути атомарні:
   запит, відхилений глобальним лімітом, не повинен списувати квоту користувача, і навпаки.
3. **Мало пам'яті й операцій на запит.** Ліміт рахується на кожен запит до `/v1`, тобто до
   200 rps на кластер. Додатковий round-trip до Redis не має з'їсти бюджет P95 < 150 мс.
4. **Керований burst.** Клієнт, що мовчав, може відправити кілька запитів поспіль; рівномірний
   потік вище ліміту має отримувати стабільну частку `429`.
5. **Передбачувана поведінка при недоступному Redis.** Це одне з питань захисту.

## Рішення

### Алгоритм

**GCRA** (Generic Cell Rate Algorithm), обидва ліміти в **одному Lua-скрипті**.

Для кожного ліміту зберігається одне число: TAT (theoretical arrival time), момент, коли
«відра» знову буде порожнє. Параметри: інтервал `T = 1 с / rate` і допуск `τ = T × burst`.

```
tat      = max(stored_tat, now)
new_tat  = tat + T
allow_at = new_tat - τ
now < allow_at  -> відмова, Retry-After = allow_at - now
інакше          -> дозвіл, Remaining = floor((now - allow_at) / T), Reset = new_tat - now
```

Скрипт рахує всі ключі (`rl:user:<id>`, `rl:global`), і лише якщо всі дозволяють, пише нові
TAT з `PX = new_tat - now`, тож ключ сам зникає, коли відро порожнє. Якщо відмовив хоч один,
нічого не записується, а `Retry-After` береться як максимум серед тих, що відмовили.

Час береться з `redis.call('TIME')`, а не з годинника gateway: репліки з розсинхронізованим
часом інакше давали б різні рішення для того самого ключа.

Ліміти за замовчуванням: користувач 20 rps з burst 20, глобально 200 rps з burst 200. Обидва в
env. Заголовки `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset` описують ліміт
користувача, бо лише його клієнт може контролювати; `Retry-After` береться з того ліміту, що
відмовив.

### Неавторизовані запити

Ліміт користувача можна застосувати лише після автентифікації. Ключ без запису в кеші gateway
означає запит у Metadata, тож перебір ключів навантажує Metadata в обхід усіх лімітів. Тому
перед зверненням у Metadata за невідомим ключем рахується третій ліміт, **за IP** (10 rps,
burst 20). Валідні ключі з кешу його не платять.

### Redis недоступний: fail-open з локальним лімітером

| Варіант                        | Що бачить клієнт, коли Redis лежить | Ризик                                    |
| ------------------------------ | ----------------------------------- | ---------------------------------------- |
| Fail-closed                    | `503` на кожен запит                | Падіння Redis кладе весь API             |
| Fail-open                      | Жодних лімітів                      | Один клієнт може перевантажити систему   |
| **Fail-open + локальний GCRA** | Ліміти приблизні, у межах репліки   | Ліміт неточний, поки Redis не повернувся |

Обираємо третій варіант. Коли виклик Redis падає або перевищує `REDIS_COMMAND_TIMEOUT_MS`,
gateway рахує ті самі ліміти в пам'яті процесу, поділені на `RATE_LIMIT_REPLICAS`. Після
помилки Redis не опитується `RATE_LIMIT_REDIS_RETRY_MS`, щоб кожен запит не чекав таймаут.
Перехід в обидва боки пишеться в лог одним рядком.

Rate limiting захищає систему, але не є функцією продукту: краще тимчасово пропустити трохи
більше, ніж відмовити всім. Решта захисту лишається: backpressure за глибиною черги, ліміти
розміру файлів і concurrency воркерів.

З цієї ж причини **Redis прибрано з readiness gateway**. Інакше Kubernetes вивів би всі поди
gateway з балансування разом з Redis, і fail-open не мав би сенсу.

## Альтернативи

### Token bucket

- Плюси: найвідоміший алгоритм, легко пояснити, природний burst.
- Мінуси: два поля на ключ (кількість токенів і час останнього поповнення), тобто `HGETALL` /
  `HSET` і дробові токени. `Retry-After` рахується з дробової частини, з помилками округлення.
- Висновок: математично GCRA і є token bucket (відро на `burst` токенів, поповнення
  `rate` за секунду), але зі станом в одне число. Поведінка та сама, реалізація простіша.

### Fixed window

- Плюси: один `INCR` з `EXPIRE`, найдешевше.
- Мінуси: на межі вікон проходить подвійний ліміт (20 запитів в кінці секунди і 20 на
  початку наступної). `Retry-After` грубий: до кінця вікна.

### Sliding window log

- Плюси: точний.
- Мінуси: sorted set з усіма мітками часу за вікно, тобто до 200 записів на глобальний ключ і
  `ZREMRANGEBYSCORE` на кожен запит. Пам'ять і CPU Redis ростуть з лімітом.

### Sliding window counter

- Плюси: два лічильники, дешевий, згладжує межу вікон.
- Мінуси: наближений (припускає рівномірний розподіл у попередньому вікні), `Retry-After`
  теж наближений.

### Ліміт у самому процесі (без Redis)

- Плюси: нуль мережевих викликів.
- Мінуси: з N репліками ліміт стає N × 20 rps і змінюється з кожним скейлом. Лишається лише як
  запасний варіант при недоступному Redis.

## Наслідки

- Позитивні: один round-trip до Redis на запит, одне число на ключ, точний `Retry-After`,
  атомарна перевірка двох лімітів. Падіння Redis не кладе API.
- Негативні: поки Redis лежить, ліміти тримаються лише приблизно. Лічильник глобального ліміту
  це «гарячий» ключ на одному шарді Redis.
- Ризики: у Redis Cluster ключі користувача і глобальний лежать у різних слотах, а Lua вимагає
  один слот. Для поточного масштабу (один Redis) це не проблема; при переході на Cluster
  глобальний ліміт рахується окремим викликом або локально з поділом на репліки, і atomicity
  між двома лімітами втрачається.
