# ADR-001. Вибір домену: Media Pipeline

- Статус: Прийнято
- Дата: 2026-10-08

## Контекст

PDP вимагає систему фонових задач, на якій можна показати: класи задач (`io`, `cpu`, `priority`),
rate limiting і backpressure, ідемпотентність і DLQ, автоскейл за глибиною черги, SLO і
навантаження 10k jobs/год при P95 < 2 хв. Домен має давати задачі з **різним профілем
ресурсів і тривалості**, інакше класи й окремий автоскейл виглядають штучно.

Розглядались два домени: Media Pipeline (картинки й відео) і Document Processing (PDF, OCR,
конвертація офісних форматів).

## Рішення

Обираємо **Media Pipeline** з трьома типами задач:

| Тип               | Інструмент             | Тривалість | Профіль             |
| ----------------- | ---------------------- | ---------- | ------------------- |
| `image.resize`    | sharp (libvips)        | десятки мс | CPU, мало пам'яті   |
| `video.frames`    | ffprobe + ffmpeg       | секунди    | CPU, IO             |
| `video.transcode` | ffmpeg H.264 480p/720p | хвилини    | CPU, багато пам'яті |

Плюс вебхуки про завершення як окремий IO-тип.

## Альтернативи

**Document Processing** (PDF -> PNG, OCR через Tesseract, DOCX -> PDF через LibreOffice headless).

- Плюс: реалістичний бізнес-кейс, теж є легкі й важкі задачі.
- Мінус: LibreOffice headless важкий (образ близько 1 ГБ), повільно стартує, нестабільний
  під паралельним навантаженням. Це шум, не пов'язаний із цілями PDP.
- Мінус: результат OCR складно перевірити автоматично (якість тексту), а розмір картинки чи
  тривалість відео перевіряється тривіально.
- Мінус: менший розкид тривалості. Між ресайзом (мс) і транскодингом (хв) три порядки, що добре
  показує, чому відео потрібен окремий клас, окремий Deployment і heartbeat.

## Наслідки

- Позитивні: природний поділ на класи і окремі пули воркерів; довгі задачі дають реальний
  привід для `msg.working()`, graceful shutdown і chaos-тесту «вбити под під час транскодингу»;
  sharp і ffmpeg безкоштовні й працюють локально.
- Негативні: образ з ffmpeg великий і має CVE (окремо розбираємось на Етапі 7); великі файли
  потребують presigned upload у S3 замість передачі через API; для відео потрібне окреме SLO
  (обґрунтування в ADR-008), бо «99% < 5 хв» для транскодингу недосяжне без великих ресурсів.
- Ризики: ffmpeg як child process (таймаути, SIGKILL, зомбі-процеси) і завантаження за URL
  (SSRF) треба закрити явно на Етапі 3.
