# Нові етапи: акаунти, медіатека, новий UI і SSG (5c), переклад відео (5d)

Доповнення до PDF «PDP Media Pipeline — покроковий план реалізації». Формат той самий: що вчити,
кроки з чекбоксами, критерій «готово, коли». Нижче — куди стають три нові пункти, нові етапи
повністю і що змінюється в уже наявних етапах.

## Що куди і чому

| Пункт                                 | Де                       | Чому саме там                                                                                                                                                                                                                                                                        |
| ------------------------------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Логін і дашборд (медіатека)           | **Етап 5c**, після 5     | Розробляється й тестується в k3d: браузери приймають cookie з `Secure` на `localhost` і `*.localhost`, а сам прапорець — у конфігу. Змінює вимоги до інфраструктури (Redis із сесіями, lifecycle і квоти в S3, піддомен `app.`), тому йде до 5b, щоб Terraform проєктувався один раз |
| Новий UI під вхід, дашборд і переклад | **5c.3–5c.4** і **5d.2** | Каркас і дизайн-система — до екранів, на початку 5c: інакше кожен новий екран тягне власні стилі й навігацію. Флоу перекладу проєктується разом з каркасом, а реалізується на 5d, коли є контракти й прогрес по кроках                                                               |
| SSG                                   | **Етап 5c**, PR 5c.5     | Пререндерити є що лише тоді, коли з'являються публічні сторінки (вхід, реєстрація, опис сервісу) і роутер. Дашборд і медіатека — персональні дані, вони лишаються клієнтськими                                                                                                       |
| Переклад відео (дубляж, `video.dub`)  | **Етап 5d**, після 5c    | Потрібні акаунти: квота хвилин і вартість рахуються на користувача, результат показується в медіатеці. До 5b, бо додає Deployment `video-dub` (розмір вузлів), секрет провайдера й egress до його API                                                                                |

Порядок: **5c** → **5d** → 5b → 6 → 7 → 8. В AWS система виходить один раз, уже з фінальним
набором сервісів; розробка нових етапів у k3d нічого не коштує, а EKS тарифікується погодинно.
Етапи 6–8 ідуть на AWS-кластері, як і в PDF, і нові можливості потрапляють у chaos, canary й
навантаження без змін у їхньому порядку.

Ціна такого порядку: AWS — найменш передбачувана частина (IRSA / Pod Identity, TLS до RDS, S3 без
статичних ключів, DNS), і її проблеми знайдуться пізніше. Тому 5b іде одразу після 5d, без інших
етапів між ними, а дешеву частину 5b.1 варто зробити вже зараз: делегувати NS від реєстратора в
Route 53 (поширення до 48 год) і перевірити бюджетний алерт.

## Етап 5c. Акаунти, медіатека, новий UI і SSG (тижні 16–19, 25 січня – 21 лютого)

**Результат етапу:** користувач реєструється і входить за email і паролем, потрапляє в новий
інтерфейс із навігацією між медіатекою, задачами, вебхуками й налаштуваннями, бачить медіатеку з
усіма своїми картинками й відео — в оригіналі й в оброблених версіях — і може їх завантажити або
видалити. Сторінки входу, реєстрації та опису сервісу приходять уже відрендереними на етапі
збірки. API-ключі лишаються для скриптів, k6 і інтеграцій.

**Вчити:** зберігання паролів (argon2id, параметри з OWASP Password Storage Cheat Sheet);
cookie-сесії проти JWT, `HttpOnly`, `Secure`, `SameSite`, CSRF і перевірка `Origin`, session
fixation; захист від перебору (rate limit на логін, однакова відповідь); модель даних для файлів
користувача, курсорна пагінація, S3 lifecycle і асинхронне видалення; client-side routing
(react-router), layout routes і lazy-маршрути; інформаційна архітектура і user flows, вайрфрейми;
дизайн-токени і примітиви дизайн-системи; доступність (WCAG 2.2 AA: фокус, клавіатура,
контраст, `aria-live` для статусів); адаптивна верстка; SSG і гідрація (`renderToString`,
`hydrateRoot`, hydration mismatch).

Етап ділиться на п'ять PR: **5c.1** вхід (бекенд), **5c.2** медіатека (бекенд), **5c.3** каркас
UI і дизайн-система, **5c.4** екрани входу, медіатеки й налаштувань, **5c.5** SSG. 5c.3 можна
вести паралельно з 5c.1–5c.2 на MSW-моках.

**Кроки (вхід, 5c.1):**

- [x] ADR-013 «Автентифікація користувачів»: cookie-сесія в Redis проти JWT, власні паролі проти
      OAuth (Google), чому API-ключі лишаються, що буде з сесіями при недоступному Redis.
- [x] Міграція: `users.email` (unique, без урахування регістру), `users.password_hash`; таблиця
      `api_keys` (кілька ключів на користувача, `last_used_at`, відкликання); наявні ключі
      переносяться з `users`.
- [x] Metadata: створення користувача, перевірка пароля (argon2id); `ApiKeyGuard` читає ключі з
      `api_keys`. Сесії живуть у Redis на Gateway (див. ADR-013).
- [x] Gateway: `POST /v1/auth/register`, `/login`, `/logout`, `GET /v1/me`; сесія в Redis,
      cookie `HttpOnly; Secure; SameSite=Lax`, новий id сесії після входу. `Secure` — з конфігу,
      увімкнений за замовчуванням: Chrome і Firefox приймають його на `*.localhost` і без HTTPS.
- [x] Guard приймає або сесію (браузер), або `X-API-Key` (скрипти); на запитах, що змінюють дані,
      сесія вимагає правильного `Origin`.
- [x] Rate limit на логін за IP і за email; однакова відповідь для неіснуючого email і
      неправильного пароля; метрика невдалих входів і алерт на сплеск.
- [x] Керування API-ключами: `GET /v1/api-keys`, `POST` (ключ повертається один раз), `DELETE`.
- [x] Свідомо поза PDP (записати в ADR): відновлення пароля і підтвердження email, бо вони
      потребують поштової розсилки.

**Кроки (медіатека, 5c.2):**

- [x] ADR-014 «Медіатека»: `asset` як окрема сутність проти групування задач за `sourceKey`;
      скільки зберігати оригінали, квота, видалення.
- [x] Міграція: таблиця `assets` (`id`, `user_id`, `key`, `content_type`, `size`, розміри або
      тривалість, `created_at`, `deleted_at`), `jobs.asset_id`; бекфіл з наявних задач. Asset
      створюється на `POST /v1/uploads`, перша задача ставить `attached_at`; `size` старих файлів
      невідомий і лишається `null`.
- [x] Gateway: `GET /v1/assets` (курсор, фільтр «фото / відео»), `GET /v1/assets/:id` (оригінал і
      всі результати всіх задач із presigned URL), `DELETE /v1/assets/:id`. Сторінка файлу віддає
      до 50 задач, решта — `GET /v1/jobs?assetId=`.
- [x] Видалення: soft delete у транзакції з подією в outbox; воркер видаляє об'єкти оригіналу й
      результатів у S3, ідемпотентно. Поки на файлі є незавершена задача — `409 ASSET_BUSY`.
- [x] Прибирання: lifecycle-правило або janitor для завантажень, з яких так і не створили задачу
      (у MinIO — через `mc ilm`, у S3 те саме правило додає Terraform на 5b); квота сховища на
      користувача з зрозумілою помилкою при перевищенні. Обрано janitor у Metadata: lifecycle за
      префіксом видалив би й оригінали медіатеки (ADR-014). Квота — `413 STORAGE_QUOTA_EXCEEDED`.
- [x] Інтеграційний тест ізоляції: чужий asset і чужа задача дають 404 (`test/assets.int-spec.ts`).

**Кроки (каркас UI і дизайн-система, 5c.3):**

Зараз весь інтерфейс — одна сторінка `WorkspacePage` з видами «Задачі» і «Вебхуки», вхід — форма
API-ключа, а в `shared/ui` є лише стиль кнопки. Для входу, медіатеки й перекладу відео потрібні
кілька сторінок зі спільним каркасом, тому спершу — каркас і примітиви, потім екрани.

- [x] Інформаційна архітектура і user flows для трьох сценаріїв: вхід і реєстрація; завантаження →
      обробка → медіатека; завантаження відео → переклад → перегляд результату (флоу перекладу
      реалізується на 5d, але проєктується зараз, щоб каркас його вмістив).
- [x] Вайрфрейми ключових екранів (Figma або FigJam): вхід, медіатека, сторінка файлу, діалог
      завантаження з вибором дії, екран перекладу; мобільна й десктопна версії. Їх же показати на
      захисті. SVG у `docs/design/wireframes/` замість Figma.
- [x] Дизайн-токени в CSS-змінних (кольори, типографіка, відступи, радіуси, тіні) на основі
      наявного стилю; світла тема. `--tone-warning` і `--tone-success` для тексту: `--amber` і
      `--green` не тягнули 4.5:1.
- [x] Примітиви в `shared/ui`: `Button`, `Input` і `Field` з помилкою, `Select`, `Checkbox` /
      `Radio`, `Card`, `Badge` статусу, `Progress`, `Dialog`, `Toast`, `Tabs`, `Skeleton`,
      `EmptyState`, `ErrorState`. Без бізнес-логіки й мережі; тести на поведінку й клавіатуру.
      `Checkbox` / `Radio` у `ChoiceGroup`; плюс `PageHeading` і `VisuallyHidden`.
- [x] react-router з layout routes: публічний каркас (`/`, `/login`, `/register`) і каркас
      застосунку з навігацією й меню користувача (`/library`, `/library/:id`, `/jobs`,
      `/webhooks`, `/settings`); захищені маршрути ведуть на вхід зі збереженням адреси
      повернення; сторінки — lazy-чанки. react-router 8, data mode.
- [x] Перенести наявне в нові сторінки: `JobsView` і `ContactSheet` — у `/jobs`, `WebhooksView` —
      у `/webhooks`, `UploadPanel` — у діалог завантаження, доступний з будь-якої сторінки;
      `LanguageSwitch` — у меню користувача і публічну шапку.
- [x] Кожен асинхронний екран має стани завантаження, помилки й порожній; статуси задач
      оголошуються через `aria-live`.

**Кроки (екрани входу, медіатеки й налаштувань, 5c.4):**

- [x] Фіча `auth`: форми входу й реєстрації з валідацією, помилки сервера (`401`, `429` з
      `Retry-After`), вихід; стан сесії з `GET /v1/me`, на `401` — перехід на вхід. API-ключ
      більше не живе в `localStorage`, фіча `api-key` прибирається. `features/auth` замінила
      `api-key` і `session`: браузер працює лише з cookie-сесією, старий `pdp.apiKey` стирається
      з `localStorage`; дев-акаунт — `seed-user --email --password`.
- [x] Медіатека (дашборд): сітка прев'ю (мініатюра для фото, кадр-прев'ю для відео), фільтри
      «фото / відео» й за статусом обробки, пошук за назвою, нескінченна прокрутка за курсором,
      стан фільтрів у URL; порожня медіатека веде до завантаження. Дані — RTK Query
      `infiniteQuery` (кеш на набір фільтрів); бекенд отримав `GET /v1/assets?status=&q=`;
      живі статуси — опитування 3 с, поки є файл в обробці або завантаження, якого ще немає у
      списку.
- [x] Сторінка файлу: оригінал поруч із версіями (розміри, вага, формат), програвач для 480p /
      720p, завантаження оригіналу й кожної версії, видалення з підтвердженням, задачі цього
      файлу зі статусами й посиланням на трейс. Завантаження — `downloadUrl` /
      `originalDownloadUrl` (presigned GET з `Content-Disposition: attachment`, бо атрибут
      `download` не діє для іншого origin); посилання стабільні в межах 5-хвилинного вікна.
- [x] Діалог завантаження: файли, вибір дії (розміри картинок, кадри, транскодинг; переклад
      з'являється на 5d), прогрес завантаження; після старту — перехід у медіатеку. Прогрес,
      відлік і помилки — на плитках медіатеки; веб надсилає `name`, щоб пошук мав що шукати.
- [x] Налаштування: профіль (email), API-ключі (створити — ключ показується один раз, список з
      `last_used_at`, відкликати), мова інтерфейсу. `LanguageSwitch` переїхав у
      `features/language`; показаний ключ прибирається зі стора одразу після відповіді.

**Кроки (SSG, 5c.5):**

- [ ] SSG: `entry-server.tsx` з `renderToString` і скрипт збірки, що пререндерить публічні
      маршрути (вхід, реєстрація, опис сервісу) українською та англійською в `dist`.
- [ ] Клієнт: `hydrateRoot` замість `createRoot`; звернення до `window`, `localStorage` і
      `navigator` прибрані з ініціалізації (`i18n.ts`, `createStore`, URL-параметри) в ефекти.
- [ ] Перший клієнтський рендер збігається з серверним, сесія читається після гідрації — без

- [ ] nginx роздає пререндерені сторінки (`try_files $uri $uri/index.html /index.html`), решта

- [ ] ADR-015 «Пререндер фронтенду»: що пререндериться, що лишається клієнтським і чому; SSG
      проти SSR.
- [ ] Тести: пререндер працює без `window`; сценарії входу, медіатеки й видалення у Vitest + MSW;

**Готово, коли:** у k3d на `http://app.pdp.localhost:19080` можна зареєструватися, увійти й
побачити медіатеку з оригіналами та всіма версіями (на домені — після Етапу 5b); наявні задачі й

екрані; чужі файли недоступні (тест); видалення прибирає об'єкти зі сховища; HTML
сторінок входу й реєстрації вже містить розмітку (видно через `curl`), а гідрація проходить без
попереджень у консолі; k6-сценарії та скрипти працюють через API-ключі, як і раніше.

## Етап 5d. Переклад відео (тижні 20–23, 22 лютого – 21 березня)

**Результат етапу:** користувач завантажує відео (до 5 хвилин), обирає «Перекласти на німецьку» і
отримує MP4 з тим самим таймлайном і німецькою доріжкою; оригінальна доріжка лишається другою,
плюс німецькі субтитри VTT. Збій або ліміт зовнішнього API не губить задачу і не змушує платити за
вже зроблений крок удруге.

**Вчити:** розпізнавання мовлення з таймкодами сегментів (Whisper) і визначення мови; машинний
переклад з обмеженням довжини; TTS; ffmpeg: `adelay`, `amix`, `atempo`, ducking
(`sidechaincompress`), кілька аудіодоріжок у MP4, `disposition` і мовні теги; робота з платними
зовнішніми API: чекпоінти, ідемпотентність, circuit breaker, бюджет; секрети в Kubernetes;
UI довгих багатокрокових процесів (прогрес по кроках, відновлення після перезавантаження
сторінки), HTML5 video, `<track>` і WebVTT.

Етап ділиться на два PR: **5d.1** конвеєр перекладу (бекенд), **5d.2** UI перекладу. 5d.2 можна
почати на фейковому провайдері, щойно готові контракти з 5d.1.

**Кроки (конвеєр, 5d.1):**

- [ ] Спайк на 1–2 дні: скрипт ffmpeg → `whisper-1` → переклад → TTS на хвилинному відео; виміряти
      час, вартість і зсув фраз відносно оригіналу. Нотатки в `docs/spikes/`.
- [ ] ADR-016 «Переклад відео»: хмарні провайдери проти self-hosted (faster-whisper, NLLB, Piper);
      закадровий голос проти розділення голосу й фону (Demucs); одна задача з чекпоінтами проти
      ланцюжка задач; передача аудіо третій стороні.
- [ ] Контракти: тип `video.dub`, `VideoDubInputV1` (`sourceKey`, `targetLanguage`,
      `sourceLanguage` за замовчуванням `auto`), `VideoDubOutputV1` (визначена мова, файли, VTT,
      статистика підгонки).
- [ ] Для UI: прогрес задачі з поточним кроком (`extract`, `transcribe`, `translate`, `voice`,
      `mix`) і відсотком усередині кроку; транскрипт — сегменти з таймкодами, оригінальним і
      перекладеним текстом — доступний через `GET /v1/jobs/:id` або окремий ендпоінт.
- [ ] Інтерфейси `SpeechToText`, `Translator`, `TextToSpeech`; адаптери OpenAI і фейковий
      провайдер для тестів, k6 і k3d без ключа. Інтерфейс потрібен і тому, що сегментні таймкоди
      зараз дає лише `whisper-1`, а його планують вимкнути.
- [ ] Процесор: витягнути аудіо → розпізнати сегменти й мову (та сама мова, що й цільова, або
      немає мовлення — `PermanentError`) → перекласти всі сегменти одним запитом із бюджетом
      символів на сегмент → озвучити кожен сегмент → підігнати під слот → звести доріжку →
      змонтувати з `-c:v copy`, без перекодування відео.
- [ ] Підгонка: фраза займає паузу до наступного сегмента, далі прискорюється `atempo` не більше
      ніж у 1.4 раза, далі перекладається коротше; сповільнення немає.
- [ ] Фон: оригінал приглушується під час мовлення (закадровий голос), німецька доріжка — за
      замовчуванням, оригінальна — другою, з мовними тегами `deu` / `eng`.
- [ ] Чекпоінти: кожен крок кладе артефакт у `results/{jobId}/dub/`; повтор і передана після
      scale-down задача продовжують з останнього готового кроку.
- [ ] Помилки провайдера: `429` і `5xx` — transient з `Retry-After`, `4xx` — permanent; таймаут на
      кожен виклик; circuit breaker, щоб не палити ретраї під час аварії провайдера.
- [ ] Окремий Deployment `video-dub` (`VIDEO_JOB_TYPES=video.dub`) з KEDA за лагом: він хвилинами
      чекає на API і не повинен займати слот транскодингу. Секрет з ключем провайдера, egress
      лише до API провайдера (NetworkPolicy).
- [ ] Ліміти й гроші: тривалість до 5 хвилин, квота хвилин дубляжу на користувача на місяць,
      лічильник секунд аудіо й символів як оцінка вартості.
- [ ] Observability: span на кожен крок, тривалість кроків, частка прискорених і перекладених
      коротше сегментів; окремий SLO для `video.dub` з порогом, обґрунтованим в ADR-016; дашборд.
- [ ] Тести: unit на алгоритм підгонки й аргументи ffmpeg; інтеграційний з фейковим провайдером;
      «вбити под посеред дубляжу» не дає ні втраченої задачі, ні повторного платного виклику.

**Кроки (UI перекладу, 5d.2):**

- [ ] Діалог завантаження: для відео — дія «Перекласти», цільова мова, мова оригіналу («визначити
      автоматично» за замовчуванням); перед стартом — тривалість, залишок квоти хвилин і
      попередження, якщо відео довше за ліміт.
- [ ] Екран обробки: кроки (витяг аудіо → розпізнавання → переклад → озвучка → зведення) з
      поточним кроком і прогресом, визначена мова, щойно вона відома; стан переживає
      перезавантаження сторінки й повертається з медіатеки; помилки зрозумілою мовою (немає
      мовлення, мова вже цільова, ліміт провайдера — повторимо пізніше).
- [ ] Сторінка результату: програвач з перемиканням «оригінал / переклад» (два файли, бо
      браузери не дають вибрати аудіодоріжку в MP4), субтитри через `<track>` (VTT), завантаження
      MP4 і VTT.
- [ ] Транскрипт поруч із програвачем: сегменти з таймкодами, оригінал і переклад у дві колонки,
      клік — перехід на цей момент, поточний сегмент підсвічується під час відтворення; позначки
      прискорених і скорочених сегментів.
- [ ] Медіатека: у відео — бейдж «є переклад: DE», переклад як ще одна версія на сторінці файлу;
      фільтр «з перекладом».
- [ ] Стани порожній, завантаження, помилка на кожному екрані; тести флоу у Vitest + MSW з
      фейковими подіями прогресу.
- [ ] За бажанням (друга версія): Demucs в окремому Python-сервісі, щоб зберегти музику й ефекти
      без оригінального голосу; діаризація і різні голоси для мовців; локальні провайдери для
      демо без ключів.

**Готово, коли:** хвилинне англійське відео стає німецьким, і фрази починаються не далі ніж
приблизно за 0.5 с від оригіналу; оригінальна доріжка лишається другою; увесь шлях — вибір мови,
прогрес по кроках, перегляд з перемиканням доріжок і транскриптом — проходиться в UI без API і
консолі; вбитий под або `429` від
провайдера не дають втраченої задачі чи повторного платного кроку (видно в метриках); вартість
хвилини дубляжу порахована.

## Що змінюється в наявних етапах

**Етап 1.** Пункт «Простий auth: API-ключ користувача в заголовку. Повноцінний auth не є метою
PDP.» — доповнити: «API-ключ лишається для машинних клієнтів; вхід для людей з'являється на
Етапі 5c.» Зробленого на Етапі 1 це не змінює.

**Етап 5b** (тепер після 5c і 5d; деталі — у [плані 5b](stage-5b.md#що-додають-етапи-5c-і-5d)):

- [ ] Redis зберігає сесії: персистентність і PVC, а вибір «у кластері чи ElastiCache» в ADR-017
      враховує, що падіння Redis тепер розлогінює користувачів.
- [ ] S3: роль воркера з `s3:ListBucket` і `s3:DeleteObject` на бакет медіа. Lifecycle-правило
      для `uploads/` без задачі не потрібне: їх прибирає janitor Metadata (ADR-014).
- [ ] Ключ провайдера дубляжу: SSM SecureString у Terraform → Secret у namespace `pdp`.
- [ ] Розмір вузлів і `values-aws.yaml` враховують Deployment `video-dub`; egress до API
      провайдера дозволений NetworkPolicy (network policy у `vpc-cni`).
- [ ] Smoke-тест після деплою: вхід і медіатека поруч з `image.resize`.

**Етап 6:**

- [ ] Coverage 80% включає вхід, сесії, медіатеку й алгоритм підгонки дубляжу.
- [ ] Pact: нові ендпоінти Metadata (користувачі, сесії, assets); message pact для `video.dub`.
- [ ] Chaos: недоступний або повільний провайдер дубляжу (Toxiproxy перед API), pod kill
      `video-dub` посеред задачі, Redis недоступний — що відбувається з сесіями і логіном.
- [ ] E2E у браузері (Playwright) на три флоу: реєстрація і вхід; завантаження → медіатека →
      видалення; переклад відео з фейковим провайдером. Автоматична перевірка доступності (axe) на
      ключових екранах.

**Етап 7:**

- [ ] Canary і для `video-dub`.
- [ ] За бажанням: пререндерений фронтенд у S3 + CloudFront з інвалідацією в CI.

**Етап 8:**

- [ ] Змішане навантаження додає логін і `video.dub` з фейковим провайдером.
- [ ] Cost per 1k jobs окремо для `video.dub`: вузли плюс ціни провайдерів за хвилину.
- [ ] Профіль argon2 під навантаженням логіну.

**Фінальна прожарка:**

- [ ] Демо: реєстрація → завантаження відео → переклад на німецьку з прогресом по кроках →
      перегляд з транскриптом → медіатека з оригіналом і версіями.
- [ ] Вайрфрейми й user flows з 5c.3 — серед артефактів.
- [ ] ADR 001–017 з альтернативами й trade-offs.
- [ ] Питання, до яких підготуватися: чому cookie-сесія, а не JWT? Що буде з сесіями, якщо впаде
      Redis? Як не платити двічі за повтор задачі дубляжу? Як зберігається таймлайн, якщо
      німецька довша за англійську?
