# Етап 2. Rate limiting і backpressure

- Тижні 6–7: 16–29 листопада 2026
- Статус: в роботі, гілка `feature/stage-2-rate-limiting`

## Результат і критерій

**Результат:** API тримає 20 rps на користувача і 200 rps глобально, віддає `429` з коректним
`Retry-After`, а при переповненій черзі не приймає нові задачі. P95 API нижче 150 мс.

**Готово, коли:**

- k6 thresholds проходять;
- частка `429` відповідає налаштованим лімітам;
- при штучно забитій черзі Gateway віддає `503` замість росту затримки.

## Прийняті рішення

| Питання                   | Рішення                                                                                                  |
| ------------------------- | -------------------------------------------------------------------------------------------------------- |
| Алгоритм                  | GCRA, один Lua-скрипт перевіряє ліміт користувача і глобальний ([ADR-005](../adr/0005-rate-limiting.md)) |
| Redis недоступний         | Fail-open з локальним GCRA в пам'яті, ліміти поділені на кількість реплік                                |
| Неавторизовані запити     | Окремий ліміт за IP, рахується лише для ключів, яких немає в кеші                                        |
| Що вважати глибиною черги | `state.messages` WorkQueue-стріму класу: і ті, що чекають, і ті, що в обробці                            |
| Кого зупиняє backpressure | Лише `POST /v1/jobs`, і лише якщо переповнений стрім класу цієї задачі                                   |
| Вибір класу               | `selectClass` переїхав у `libs/contracts`: його використовують scheduler і gateway                       |
| Readiness gateway         | Без Redis: при fail-open падіння Redis не повинно виводити поди з балансування                           |
| k6                        | Docker-образ `grafana/k6` у мережі compose, без локальної установки                                      |

## Задачі

### Rate limiting

- [x] ADR-005 «Алгоритм rate limiting»: token bucket, sliding window і GCRA, fail-open чи fail-closed.
- [x] Lua-скрипт GCRA: кілька ключів за один виклик, час з `redis.call('TIME')`, all-or-nothing.
- [x] Локальний GCRA з тією самою семантикою як запасний варіант, коли Redis не відповідає.
- [x] `RateLimitGuard`: `429`, `Retry-After`, `RateLimit-Limit` / `RateLimit-Remaining` / `RateLimit-Reset`.
- [x] Ліміт за IP для невідомих ключів у `ApiKeyGuard`, `TRUST_PROXY_HOPS` для роботи за nginx.
- [x] Ліміти в env: `RATE_LIMIT_USER_RPS`, `RATE_LIMIT_GLOBAL_RPS`, burst, `RATE_LIMIT_REPLICAS`.

### Backpressure

- [x] `QueueDepthService`: глибина стрімів класів з кешем `QUEUE_DEPTH_CACHE_MS` (1 с), один запит до NATS на всі виклики.
- [x] `POST /v1/jobs` віддає `503` з `Retry-After`, якщо стрім класу задачі глибший за поріг.
- [x] Пороги в env: `BACKPRESSURE_MAX_DEPTH_CPU` / `_IO` / `_PRIORITY`.
- [x] Воркер: перевірити й описати зв'язок `WORKER_CONCURRENCY` і `max_ack_pending`.
- [x] Ліміт одночасних завантажень на один хост у воркері (для завантаження за URL на Етапі 3).

### Клієнт

- [x] Web UI: `429` і `503` показуються з часом очікування, створення задачі повторюється після `Retry-After`, polling сповільнюється.

### Тести і навантаження

- [x] Unit: GCRA (межі burst, `Retry-After`, all-or-nothing), guard, backpressure.
- [x] Інтеграційні (Testcontainers): ліміти на справжньому Redis, Redis зупинено (fail-open), забита черга дає `503`.
- [ ] k6 у `perf/k6`: `api-baseline` (P95 < 150 мс), `rate-limit` (частка `429`), `spike`, `backpressure`.
- [ ] autocannon на `GET /v1/jobs/:id`.
- [ ] Звіт `perf/reports/stage-2.md`: цифри, графіки, висновки.

## Що з'ясувалось під час реалізації

- **`max_ack_pending` спільний для всіх реплік воркера.** Це ліміт durable consumer, а не
  процесу. Попереднє значення `2 × WORKER_CONCURRENCY` обмежило б увесь кластер чотирма
  повідомленнями в польоті, скільки б реплік не запустили. Тепер це окремий
  `WORKER_MAX_ACK_PENDING` (256): він має бути не меншим за «максимум реплік × concurrency».
  Власну паралельність процес і далі тримає семафором на `WORKER_CONCURRENCY`.
- **`POST /v1/uploads` backpressure не зупиняє.** Завантаження не додає роботи в чергу; зупинка
  на ньому лише змусила б клієнта завантажити файл двічі. Клієнт отримує `503` на
  `POST /v1/jobs` і повторює саме його, файл уже в сховищі.
- **Одночасні запити з одним новим ключем ділять один lookup.** Без цього холодний кеш після
  деплою давав десятки однакових запитів до Metadata і вичерпував IP-ліміт для невідомих ключів.
- **Зависання Redis не повинно блокувати зупинку.** `quit()` чекає відповіді й падає по
  `commandTimeout`, тому при помилці з'єднання просто рветься.
